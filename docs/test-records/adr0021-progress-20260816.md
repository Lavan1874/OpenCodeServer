# ADR 0021 — Signing identity migration progress

Date: 2026-08-16  
Target: macOS 26.6.1 (25G76), Apple Silicon  
Branch: `adr0021/signing-migration`  
Scope: ADR 0021 Phase 0–4 only

This is an interim record. Phase 4 is not complete because the required Local
Network `AttributionChain` acceptance could not be established from the
available system evidence. No Phase 5 expiry experiment or Phase 6 re-sign was
performed.

## Phase 1 — signing configuration

The Release path now uses the Apple Development identity in
`Config/Release.xcconfig`, `scripts/build.sh`, and the required signing
authority gate in `scripts/install.sh`. `Config/Base.xcconfig` remains ad hoc;
Debug, test, and CI behavior retains its test override capability.

`scripts/xcode-build-rust.sh` was intentionally unchanged. Release builds
verified that it inherits `EXPANDED_CODE_SIGN_IDENTITY` and retains
`--timestamp=none` and `--options runtime`.

The installer and requirement-checking scripts have an explicit identity
migration mode for the one-way old-to-new Designated Requirement change. The
default same-identity mutual-requirement behavior remains intact. Shell syntax,
diff checks, fail-closed authority checks, and the existing installer test
passed.

## Phase 3 — migration install and expected self-heal

The installed Build 73 `OpenCodeServer` GUI received a normal quit request.
Neither `OpenCodeServerAgent` nor `OpenCode` was stopped. Build 74 was then
installed atomically using the identity-migration installer path and the app
was reopened.

The expected stale-cdHash event occurred exactly once:


### FDA probe

The authenticated `OpenCodeServerAgent` status remained:

```text
Full Disk Access = NotVerified
```

No TCC database was read, parsed, or modified. This is a tri-state functional

### mDNS and Local Network observation

The user enabled mDNS in Settings → Advanced, saved, and chose the prompted
OpenCode restart. The resulting persisted configuration and process were:

```text
MDNS = true
/opt/homebrew/bin/opencode serve --hostname 10.0.0.254 --port 4096 --mdns
OpenCode health = healthy
```

No visible Local Network authorization dialog appeared. The relevant Unified
Logging evidence was:

```text
Local network allowed by preference for OpenCodeServerAgent
(ai.opencode.server.agent), but received prompt. Clearing cached UUIDs and
restarting session.
```

The user manually inspected System Settings → Privacy & Security → Local
Network and observed:

```text
OpenCodeServerAgent       off (two entries)
opencode-launcher         on  (two entries)
```

This does not establish the required ADR/AGENTS.md acceptance:

```text
responsible = ai.opencode.server
accessing   = /opt/homebrew/Cellar/opencode/<version>/bin/opencode
```

The two `opencode-launcher` entries are not OpenCodeServer components and
were not changed. The two disabled `OpenCodeServerAgent` entries do not
provide evidence that the current Build 75 responsibility chain is accepted.
Because no prompt attribution was visible and no supported, clean-state
attribution result was available, the Local Network acceptance is unresolved.

No System Settings UI automation, privacy-database inspection, permission
toggle, service cleanup, or unplanned experiment was performed.

## Addendum — 2026-08-16 ~12:30, reviewer verification of the two open items

### FDA acceptance — COMPLETE

After the operator granted Full Disk Access to `/Applications/OpenCodeServer.app`
and ran Advanced → Recheck Full Disk Access, authenticated status reports
`fda = verified` (`opencodeserverctl status --json`; the human-readable
output line is `Full Disk Access: Verified`). The menu shows no FDA row by
design — the conditional informational row appears only while not Verified.

Unified Logging additionally captured the full responsibility chain under
the new identity at 12:23:34:

```text
tccd: Handling access request to kTCCServiceSystemPolicyAllFiles,
from Sub:{ai.opencode.server}
Resp:{TCCDProcess: identifier=ai.opencode.server.agent, …,
binary_path=/Applications/OpenCodeServer.app/Contents/Resources/
OpenCodeServerAgent.app/Contents/MacOS/OpenCodeServerAgent},
ReqResult(Auth Right: Allowed (System Set), promptType: 1, DB Action:None)
```

This is the FDA AttributionChain evidence: responsible = ai.opencode.server,
accessing = the embedded agent, resolved under the Apple Development identity.

### Local Network — functionally granted; formal clean-state attribution
### re-test still pending

The two `OpenCodeServerAgent` rows in Local Network settings toggle together
(one client identity; the duplicate rows are the identity transition's
presentation). The operator enabled them at ~12:22; nehelper then logged
`Caching 1 UUID(s) for ai.opencode.server.agent` with no further prompt or
denial churn, and an OpenCode restart issued over IPC (`opencodeserverctl
restart`, 12:27) returned to healthy in 1.0 s with `--mdns` intact and no
Local Network messages at all (clean allow).

Earlier corroboration: securityd's 11:38 keychain prompt dump shows the
item's pre-seeded ACL subjects still anchored to the outgoing self-signed
  root (`certificate root = H"<self-signed-sha1>…"`) — the expected one-time consent under
ADR 0016 for the identity change; and nehelper's 11:48
"allowed by preference … but received prompt. Clearing cached UUIDs"
records the pre-toggle transitional state.

What remains open is the formal acceptance from AGENTS.md/ADR 0018: the
`responsible = ai.opencode.server / accessing =
/opt/homebrew/Cellar/opencode/<version>/bin/opencode` chain and prompt-name
quality can only be observed from a state with no cached Local Network
preference. This machine now permanently holds an allowed preference, so
that re-test must run on restorable clean state (as the Build 64 test did),
and is now meaningful precisely because the signing model changed. Until
then, Local Network attribution acceptance stays open by design, not by
defect.
